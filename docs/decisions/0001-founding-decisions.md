# 0001. Founding decisions

Status: a living record while the project is in planning. Each row says what was chosen, what was rejected and why, and whether it is settled. Dates are when the maintainer ruled. Section references point to [../intent.md](../intent.md); research references point to [../research/](../research/).

| # | Decision | Chosen | Alternatives and why not | Status |
|---|---|---|---|---|
| D0 | What the product is | One thing: an MCP server that serves a company's OKF bundle to agents, on a developer's machine or hosted. It states what it needs from a bundle (the intake contract, intent §3) and ships recipes beside it for publishing, deploying and keeping current. Checks, scaffolding and intake are not product | An earlier draft's kit of seven commands covering validate, publish, deliver, fetch, serve and more: too broad; serving is the actual problem | Settled, 2026-10-06 |
| D1 | Name and licence | Name `okf-catalog`, chosen 2026-10-06 after a check found no competing project; the exact name is free on npm and GitHub (similar names exist: a dormant skill named `claude-okf`, some config file names). Site `okfcatalog.dev`, unregistered when checked the same day; `okfcatalog.com` is taken. GitHub Pages on the domain. Licence: Apache-2.0 recommended. It is the licence of the OKF specification, of Google's Knowledge Catalog, of superops okf and of the MCP SDK, which is moving from MIT to Apache-2.0 (`@modelcontextprotocol/server` 2.3.1, released 2026-10-05, is Apache-2.0); it carries an explicit patent grant; it sits fine on MIT dependencies such as qmd; with it, a NOTICE file and a contributor licence agreement (D56) rather than a DCO sign-off, because the agreement's sublicensing grant is what keeps a later move to the AGPL or to commercial terms for a hosted edition possible, and a DCO grants nothing of the kind. The one cost: code under it cannot be copied into an MIT project such as qmd without relicensing, which the maintainer can grant for his own code | MIT: shorter, no patent grant, what qmd uses, and the same for a hosting business (neither licence stops another host). Dual MIT and Apache-2.0: paperwork for no gain. AGPL now: open source, but would make companies hesitate to adopt the code internally; kept as the option the agreement preserves. Other names: `okf-library`, `okf-shelf`, `okf-stacks`; `okf-catalog.dev` with the hyphen | Settled, 2026-10-07: Apache-2.0 |
| D2 | Language, and how qmd is used | TypeScript, Node 22 or later; qmd used as a library through its SDK (`@tobilu/qmd`: `createStore`, `update`, `search`, `searchLex`, `get`, `getDocumentBody`), never as a child process; the `qmd` command is not a run-time dependency, and its shell hook is never used | Go: would re-implement or shell out to qmd. Shelling out to the CLI from TypeScript: a process per query, the CLI's own config and model downloads, no typed results | Settled, 2026-10-06 |
| D3 | Validation | Not the product. The server checks its contract on load. The publish recipe runs existing OKF checkers (okflint, okf-schema); a trial of okf-core and the okf-skills validator decides whether the recipe ever needs more | A validator of our own: re-owning what maintained tools already do | Settled, as a recipe |
| D4 | Publish target | A git branch named `published`, fetched by the server | Tags: do not move on pull. Registries: new credentials | Settled |
| D5 | Where the bundle lives at run time | Pulled by the server into its own cache; never inside a plugin | Inside the plugin: stale under harness update rules | Settled |
| D6 | Retrieval base and pin | qmd, npm release 2.8.3 (`facd35e`); filters from the manifest until a release ships the metadata filter; the collection-scope defect on that release worked around by over-fetching | Track main: filter now, churn forever. superops okf: see research/retrieval-engines.md | Open; the release is recommended |
| D7 | Modes | Lexical-only default everywhere; full mode opt-in. Reservation recorded: if full mode changes results dramatically, the default is wrong; so the lexical-versus-full measurement is a version 0 item, on one laptop, on the benchmark corpus and the acceptance questions, and the default is a one-line setting per company either way. qmd's two modes have not been measured against each other yet | Full by default: 2.3 GB on every machine and every container | Settled with a reservation, 2026-10-06 |
| D8 | First clients | Claude Code locally; claude.ai web in version 1; Codex and Grok Build next | | Settled |
| D9 | OKF 0.2 texts | The server reads both date forms (a date alone in the 15 August 2026 text, a datetime in the 21 August text); the contract lets a company pin one | | Proposed |
| D10 | What the server serves | Pages passing the company's status rule, default `stable` and `deprecated`; a development flag admits drafts and labels them, local mode only | | Settled; one page of the first bundle to promote before the first real publish |
| D11 | Fetched content | Never executed. Git pull, then qmd's library re-index; no shell hooks; a `.qmd` config inside a bundle is refused | | Settled |
| D12 | Remote authentication | The server is an OAuth resource server (RFC 9728 protected-resource metadata through the MCP SDK's `requireBearerAuth` and `mcpAuthMetadataRouter`), because OAuth is the one credential claude.ai, ChatGPT and grok.com all accept; a static bearer is also accepted for the local CLIs. The authorization server is not written by us (D12b) | A fixed bearer header: claude.ai beta only, ChatGPT never. An external proxy with no owner | Settled in shape; D12b open |
| D12b | Authorization server for cloud mode | Open: a hosted provider that speaks MCP's OAuth profile with dynamic client registration, or Google Workspace or GitHub if a platform accepts them; to be researched before the version 1 spike | Writing an authorization server ourselves | Open |
| D13 | One instance per company | Separate process, database, cache, credential, skill id | A multi-tenant server | Settled |
| D14 | Cloud targets for the recipe | Google Cloud Run first (a public service with application-level auth, since the web agents cannot present a Google identity token; one minimum instance; qmd's allowed-hosts setting configured), then a Hetzner VPS recipe as the non-Google equivalent | Fly.io, Render, Railway: same price band, documented as alternatives, not maintained as recipes | Proposed |
| D15 | How the cloud server gets the bundle | Baked into the image by CI on each publish, so the running server holds no GitHub credential | A read-only deploy key with a timer pull: works, but puts a credential in the container | Proposed |
| D16 | Keeping the server current | Locally, a timer pull in the server process, default ten minutes. In the cloud, a new deploy per publish, from CI | Webhooks: need an inbound endpoint and a secret | Proposed |
| D17 | Contribution to superops okf | Outside this project; a goodwill pull request if the maintainer wants | | Open |
| D18 | Google Docs intake, scaffold, multi-repository aggregation | Future ideas, listed, not scheduled | | Settled |
| D19 | Who shapes pages for the engine | The server, in a derived copy in its own cache: it writes the `qmd: metadata:` block and the title, description and tags lines itself, and `get_page` serves the original; companies publish plain OKF (intent §6). This is the value proposition: qmd done right for OKF | The publisher pre-shapes each page: couples every company's publish step to qmd's conventions | Settled, 2026-10-06 |
| D56 | Contributions | Every outside contribution is covered by the Contributor License Agreement in `CLA.md` (adapted from the Apache ICLA 2.2, with a grant to sublicense under any terms and an assignment clause), signed once by a comment on the first pull request and recorded by the CLA Assistant action in `.github/cla/signatures.json` on the `cla-signatures` branch; the text is to be reviewed by a lawyer before the first outside contribution is accepted | A DCO sign-off (no relicensing right); a copyright assignment (contributors dislike it; the sublicensing grant is enough) | Settled, 2026-10-07 |

Refinements proposed by the implementation plan ([../plans/version-0.md](../plans/version-0.md), section 4), awaiting the maintainer's ruling: D19 is kept, but version 0 renders no `qmd: metadata:` block, because the current qmd release ignores it (D30 there); D25 there settles one qmd collection per company with the server's own candidate pool; D27 there launches the plugin's server with `node` on a configured path rather than `npx`; D28 to D31 there cover index locking, the two staleness rules, the metadata block and the lexical keyword contract.

Retired from earlier drafts: a fetch script shipped to every machine (the server pulls for itself); a search gate before serving (serving is the product); an external auth proxy (auth is in the server).
