## 2. The architect's brief (carried over)

Architectural brief for the ticket set (issues #2 to #5), 2026-10-07.

Written by the architect for the plan's drafter and its reviewers. The four tickets are Grok's, filed under the maintainer's account; they are precise and should be taken at their word where they describe the code, and checked against the code where they prescribe. The maintainer's priority: the filters (#4) and the graph (#5) matter most to him. The plan covers the set as one, in bites, each with its own release.

### The order, and why

1. **Readiness fixes** (cut out of #2's "absent" and "partly true" lists and #3's "fields this ticket also closes"), release 0.2.0 together with #4. These are small, independent, and two of them are enablers: the typed contract fields (`runtime`, `parameters`, `computation`, `executor`, `attester`) and the one window-inheritance function are what #5 reads; the unknown status served as written (and the output schema widened) is what makes #4's status filter mean something. The rest: the spec's concept id accepted by `get_page` (the path without `.md`, with the ambiguity rule #3 states, applied to one bundle now), a v0.1 top-level `timestamp` read as `generated.at` and a `# Citations` list read as `sources` when the v0.2 fields are absent (the drafter checks the pinned spec's text for the v0.1 forms before specifying the parse), a non-numeric `usage_count` dropped and reported, the page-level `usage_window` typed and surviving the 8 000-character omission. Each is a day or less and gets its own test. Landing them apart keeps #3's diff to the architecture.
2. **#4, the filters**, as written, with the behaviour change it carries: an omitted freshness argument includes overdue pages, flagged. That is a decision row, not a footnote. The harness proves the filters change no rank (the lexical rows stay identical).
3. **#5, the graph tools**, as written, on one bundle; the `bundle` argument and the cross-bundle ambiguity error arrive with #3 and must be designed so that #5's lookup takes them without a rewrite (one resolver, used by `get_page`, `citations` and `provenance`).
4. **#3, the network**, as its own bite with a decision row: version 0 is one company per process and the plan's "second company" meant a second process; #3 keeps audiences apart but merges one audience's bundles in one index. The drafter resolves the design points below before the plan prescribes anything.
5. The graph across bundles, later, if ever.

Releases: 0.2.0 (fixes + filters), 0.3.0 (graph), 0.4.0 (network, with the `company:` alias kept for one release as #3 says). Every bite: plan section, tests first, build, two adversarial reviews of the build, fold, tag.

### Decisions the plan must carry (the architect's calls, to be reviewed)

- **D-A, the ledger becomes tests.** Every sentence of #2's "holds" list that no test asserts today gets a named test, so the readiness the ledger describes cannot regress unnoticed. The drafter maps each sentence to an existing test or to a new one.
- **D-B, one resolver for a page name.** A single function turns the string a caller gives (`/path.md`, `./path.md`, `path.md`, the concept id `path`) into a page or a precise error (not found with nearest paths; ambiguous with the names), used by `get_page` now and by `citations` and `provenance` next, extended by `bundle` in #3. The two-name lookup (#3 §Identity, #5 step 3 of the classifier) is written once.
- **D-C, the overdue default flips with #4**, as the ticket argues from the spec; the skill and the tool descriptions say so; `include_stale` stays an alias for one release.
- **D-D, no rank change anywhere in this set.** Filters apply after the engine returns; the graph adds no score; the network's score shift when a second bundle joins is accepted and measured, and a one-bundle network must reproduce the lexical benchmark rows exactly (a regression guard the harness runs).
- **D-E, the network's index.** The drafter must resolve, from qmd's code (node_modules/@tobilu/qmd/dist/store.js and index.js) and ours (src/engine/qmd.ts): how one collection root can hold several bundle directories so that a refresh of one bundle does not deactivate the others in qmd's `update()` (which deactivates every active path the scan did not see; verified at store.js near line 1342). Options to weigh: (i) one generation folder per network, a refresh writing the refreshed bundle's new tree beside copies or hard links of the other bundles' current trees, then one link flip and one `update()` (every path seen; unchanged content costs a hash, not a re-index, if qmd hashes); (ii) stable per-bundle directories replaced in place, with qmd's `deactivateDocument` called for the paths that vanished (racy against a concurrent scan); (iii) one collection per bundle in one database, if BM25 statistics are shared across collections so that scores stay comparable (the ticket assumes separate databases are not comparable; separate collections in one FTS table may be). Also: whether qmd's scanner follows symbolic links (our generation link today is a directory link flipped by base name) and hard links. The plan prescribes one option with its evidence.
- **D-F, the branch model.** `main` becomes the release line (fast-forwarded to `version-0`'s head and made the default branch), a feature branch per ticket, tags release; `version-0` retires once merged. The plan says when.
- **D-G, versions and the alias.** `company:` with one `source:` means a one-bundle network for one release; refused together with `network:`.

### Invariants that hold throughout

AGENTS.md and the version 0 plan: the core modules import neither qmd nor the MCP SDK nor Node's file system, process or network modules (the dependency rule in CI is the proof); the platform consumes assets through the manifest; the tools stay read-only and never execute bundle bytes; no secrets, no client names, nothing personal in the repository; tests first, each red before its code; the generation seam and the lock per process; the privacy rules of the acceptance scripts. The network keeps one process per audience; two audiences never share an index.

### What the drafter must read before writing

The four issues in full (`gh issue view 2 3 4 5 --repo drathm/okf-catalog`); `src/` as it is (search.ts, query.ts, tools.ts, text.ts, outputs.ts, contract.ts, page.ts, markdown.ts, links.ts, load.ts, provenance.ts, company-config.ts, qmd.ts, qmd-render.ts, company-lock.ts, cache-dir.ts, runtime.ts, poller.ts, git.ts); the pinned OKF 0.2 text (commit 25461db of GoogleCloudPlatform/open-knowledge-format, fetched raw; §2 ids, §5.1 sources and recursion, §6 links and path fields, §8 index, §10 attestation, §11 tolerance, and whatever it says of v0.1 compatibility); qmd's store.js (collections, `update()`, `deactivateDocument`, FTS tables and ranking, the scanner and links) and index.js; the existing tests for the modules touched; docs/intent.md, docs/plans/version-0.md (D-rows and invariants), docs/decisions/0001-founding-decisions.md, docs/research/facts.md, docs/research/benchmark-lexical.md.

### What the plan must contain

For each bite: scope in the tickets' own terms, the decision rows it adds, the files it creates or changes and what each is responsible for, the tests written first (named, with what each asserts), the build steps in order, the acceptance check (what proves the bite done, including the harness regression guard where rank could move), the documentation that changes (tool descriptions, the skill, the README, the changelog, the decision record), the release. Then the open questions the architect must rule on, each with the drafter's recommendation and evidence. No placeholders: where something is unknown, say what was read and what remains unknown. Write plainly; no marketing.

### The standing of the tickets

The tickets are Grok's proposals, written from its review of how far the server meets the OKF 0.2 text ("improving our performance to spec", in the maintainer's words). Discussion is expected. The plan treats each prescription as a proposal: where the plan follows it, it says so briefly; where it departs, it says what and why, with evidence; where the architect's calls above override a ticket (the order, the split of the small fixes, the one resolver, the regression guard, the decision rows the tickets put out of scope), the plan says so plainly. The plan ends with the list of discussion points for Grok and the maintainer: every departure, every place a ticket's prescription seems wrong or costlier than its value, and every question only the maintainer can settle. Agreement is not the goal; a plan that is right is.

## 4. The network's index (D-E)

What qmd 2.8.3 does, read and probed on 2026-10-07 (the probes ran on scratch folders outside the repository, macOS, qmd 2.8.3, fast-glob 3.3.3), and confirmed by both plan reviews (section 9):

1. **Update.** `update()` reindexes every configured collection, or those in `update({ collections })` (`index.js:190-213`, typed at `index.d.ts:190-191`). `reindexCollection` (`store.js:1253`) globs the root, reads and hashes each file, leaves one with an unchanged hash and title untouched, and deactivates every active path of that collection the scan did not see (`store.js:1342-1349`); both queries filter on the collection name (`store.js:2341-2353`). Probed: one page of collection `aa` removed, `update({ collections: ["aa"] })` gave `removed: 1, unchanged: 3` and left `bb`'s four pages active; a second run, `unchanged: 3` only.
2. **Links and skipped names.** The scan is `fastGlob` with `onlyFiles`, `followSymbolicLinks: false`, `dot: false` and the six skipped names (`store.js:1256-1272`). Probed: the root may be a link (as `derived` is, `qmd.ts:183-188`); a directory or file link below it is not indexed; a hard link is indexed as a file; the skipped names and the dot rule apply only below the root (a root at `.cache/okf-catalog/net/bundles/dist/derived` indexed both its files).
3. **Statistics.** One FTS5 table, `documents_fts(filepath, title, body)`, serves every collection of a database (`store.js:842-847`; rows kept by triggers, `filepath` = `collection/path`, `store.js:745-783`). `searchFTS` ranks by `bm25(documents_fts, 1.5, 4.0, 1.0)` (`store.js:3214`), and SQLite defines N, n(q) and avgdl over the whole FTS5 table (sqlite.org/fts5.html, the bm25 function). Probed: eight pages, a term in three of them, every hit scored 0.311287709738 in one collection and in two collections of one database, and 0.000000999999 in a separate database holding half the pages. Scores compare across collections of one database and not across databases.
4. **Deactivation.** `deactivateDocument` sets `active = 0` (`store.js:2341-2344`) and the update trigger deletes the FTS row (`store.js:768-771`), so a deactivated page leaves the statistics. The typed SDK reaches it only through `QMDStore.internal` (`index.d.ts:125`).
5. **A collection removed or emptied.** `syncConfigToDb` deletes a dropped collection's `store_collections` row (`store.js:1185-1206`) and leaves its documents active; probed, an unscoped search still returned them. The public `removeCollection` does no more: it calls `deleteStoreCollection` (`index.js:147-152`, `store.js:1137-1140`); the function that also deletes documents (`store.js:2793-2806`) is not reachable through the package, whose only export is its root; and `searchFTS` joins only `documents` and `content` and filters on `active` (`store.js:3212-3231`). An existing empty root does empty a collection: the scan sees nothing, so every page is deactivated (finding 1). `QmdEngine.open` already rebuilds a store holding another collection's rows (`qmd.ts:92-99`).
6. **Search.** `searchLex` without a collection is one query over the table with no over-fetch (`store.js:3191-3233`; `scopedCollectionNames(undefined)` is `undefined`, `store.js:3170-3172`). With one collection the inner fetch is ten times the limit and filtered after (`store.js:3211`); with several, each is searched and the lists merged by score (`store.js:3193-3196`).

The options, for a refresh of bundle A: (i) one collection per network, a generation of A's new tree plus hard links to the others' files, one flip and one `update()`, scans and hashes every bundle, O(all files) per refresh, and gives every `filepath` a segment, moving BM25, unless a one-bundle network omits it; (ii) one collection per network, a real folder per bundle swapped in place and `deactivateDocument` for vanished paths, scans every bundle too, depends on `internal`, and leaves a window without A (a link below the root is not followed, finding 2), safe only if no `update()` runs in it; (iii) one collection per bundle in the network's database flips `bundles/A/derived` as today and runs `update({ collections: ["A"] })`, never scans or deactivates the others (finding 1), and reproduces the one-bundle rows by construction, since an id equal to the old company name, or the harness's `bench`, writes byte-identical FTS rows; it costs a configuration entry per bundle and keeps finding 5's rebuild.

**Prescription: (iii).** It keeps every guarantee #3 asks for (a refresh replaces one bundle and only after its load succeeded; a failed refresh leaves the previous generation; search never returns a deactivated page; one scale for every score) with less work per refresh than #3's design, and reproduces the one-bundle rows exactly. #3's "every derived path starts with the bundle id" holds in the form qmd returns, `<id>/<path>`. Accepted and measured (D-D): a bundle id is a token in the `filepath` column of every page of its bundle, so a question word equal to an id favours that bundle, as the company name in every page does today; and each added bundle moves N, n(q) and avgdl for all. Neutral collection names would remove that bias but not reproduce the one-bundle rows; they are recorded as a later option.

**Fallback.** If a review finds a flaw in (iii), or a qmd release breaks findings 1, 3 or 5 (bite c's engine tests fail first): option (i) with hard links (finding 2), the bundle segment omitted in a one-bundle network so the guard still holds.
